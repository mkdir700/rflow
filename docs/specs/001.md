# Spec 001: Core、Runtime 与表现层架构分层

- 状态：Implemented
- 日期：2026-08-30
- 范围：rflow 业务 Core、运行时、平台适配、诊断、CLI 与未来 GPUI GUI

## 1. 背景

rflow 当前已经能够在 Linux host 与 macOS client 之间传递鼠标和键盘输入。现有实现以 CLI MVP 为中心，核心运行流程集中在 `src/main.rs`：参数解析、QUIC 生命周期、重连、输入采集、路由、状态恢复、平台注入、日志和退出处理共同存在于同一执行流程中。

现有 `router.rs` 已经形成相对纯粹的光标路由模块，`state.rs` 包含按下状态和运动去重逻辑；但业务决策仍然散落在 `main.rs`，并且 `state.rs`、平台输入模块和 wire protocol 之间存在类型泄漏。

项目未来将引入基于 GPUI 的 GUI。为了让 CLI、GUI 和将来可能出现的后台 daemon 共用同一套行为，必须先建立明确的架构分层。

本规格定义目标架构、模块接口、依赖方向和迁移验收条件。它不规定 GUI 的视觉设计，也不要求在本阶段立即引入 GPUI 依赖。

## 2. 目标

1. 建立不依赖操作系统、网络、异步运行时、CLI 或 GPUI 的业务 Core。
2. 将进程与任务生命周期集中到 Runtime，而不是散落在入口和表现层。
3. 让 CLI 与 GPUI GUI 通过同一应用接口控制 rflow。
4. 将协议编码、QUIC、平台输入和持久化实现为 Core 外部的 Adapter。
5. 将诊断与业务分离，使日志和指标能够观察系统，但不参与业务决策。
6. 保证连接中断、屏幕切换和进程退出时，按键与鼠标按钮能够一致地释放或恢复。
7. 为未来多屏、多客户端、后台常驻和 GUI 状态展示保留清晰的演进 seam。

## 3. 非目标

本规格不包含：

- GPUI 页面布局、主题、控件和交互视觉规范；
- 多客户端或任意方向屏幕拓扑的具体产品行为；
- daemon IPC 协议的立即实现；
- 替换现有 Quinn/Tokio 技术栈；
- 为只有单一实现的内部细节预先创建大量抽象接口；
- 改变当前 wire protocol 的兼容策略。

## 4. 设计原则

### 4.1 Core 决定应该发生什么

Core 接收领域事件、更新领域状态并返回待执行的 effect。Core 不直接操作设备、网络、时钟、文件、日志或 UI。

```rust
pub struct DesktopSession {
    // 私有领域状态
}

impl DesktopSession {
    pub fn handle(&mut self, event: SessionEvent) -> Vec<SessionEffect>;
    pub fn snapshot(&self) -> SessionSnapshot;
}
```

`DesktopSession` 必须是深模块：调用方只需理解少量事件、effect 和不变量，屏幕切换、按下状态迁移、重复运动过滤及异常清理等实现细节均隐藏在模块内部。

### 4.2 Runtime 决定如何执行

Runtime 拥有会话的单一写入权，串行处理命令、设备输入、网络输入和生命周期事件。它执行 Core 返回的 effect，并将可观察状态发布给表现层。

Runtime 负责：

- 启动、停止与监督异步任务；
- host/client 连接与握手；
- 重连策略和超时；
- 调用输入采集、输入注入和网络 Adapter；
- 正常退出与故障后的资源清理；
- 将内部事件投影为稳定的应用状态；
- 发布结构化诊断事实。

### 4.3 表现层表达用户意图

CLI 和 GPUI GUI 只能向 Application seam 发送命令并观察状态。表现层不得直接创建 QUIC endpoint、抓取输入设备、调用平台 API 或修改 `DesktopSession`。

### 4.4 Adapter 隔离外部机制

平台输入、QUIC、协议编码和配置存储属于 Adapter。领域类型不使用 Linux evdev code、CoreGraphics 类型、Quinn 类型或 postcard DTO 作为自身接口。

只有确实存在变化的 seam 才引入接口。Linux/macOS/Windows 输入已经有多个实现，因此平台输入 seam 是真实 seam；单一且稳定的纯函数不应为了“分层”增加浅模块。

## 5. 目标分层与依赖方向

```text
┌──────────────┐                 ┌────────────────┐
│  rflow-cli   │                 │ rflow-gui/GPUI │
└──────┬───────┘                 └───────┬────────┘
       │ AppCommand / AppEvent           │
       └──────────────┬──────────────────┘
                      ▼
             ┌─────────────────┐
             │ Application seam│
             │ RuntimeSupervisor│
             └────────┬────────┘
                      │ SessionEvent / SessionEffect
                      ▼
             ┌─────────────────┐
             │   rflow-core    │
             └─────────────────┘
                      ▲
                      │ 由 Runtime 调用 Adapter
       ┌──────────────┼───────────────┬──────────────┐
       │              │               │              │
  Platform Input  QUIC Transport  Wire Protocol  Diagnostics
```

允许的依赖方向是从外向内：表现层和 Adapter 可以依赖应用/领域类型，Runtime 可以依赖 Core 和 Adapter，Core 不依赖任何外层模块。

禁止形成以下依赖：

- Core → Tokio、Quinn、GPUI、Clap、tracing、evdev、CoreGraphics；
- GUI → 平台输入或 QUIC 实现；
- CLI → host/client 私有执行流程；
- Diagnostics → Core 状态写入；
- Protocol DTO → 成为 Core 的领域模型。

## 6. 模块职责

### 6.1 Core

建议包含以下领域概念：

- `DesktopSession`：会话状态机及唯一业务入口；
- `SessionEvent`：已经归一化的输入与生命周期事实；
- `SessionEffect`：必须由外层执行的动作描述；
- `SessionSnapshot`：只读、可复制的业务状态投影；
- `ScreenTopology`、`ScreenId`、`ScreenSize`：屏幕布局；
- `InputEvent`、`Motion`、`Button`、`Key`：平台无关输入；
- `PressedState`：物理按下状态及目标端已注入状态；
- 序列过滤和控制权迁移规则。

Core 的输入示例：

```rust
pub enum SessionEvent {
    PhysicalInput(InputEvent),
    RemoteInput(InputEvent),
    PeerReady { screen: ScreenDescriptor },
    PeerDisconnected,
    StopRequested,
}
```

Core 的输出示例：

```rust
pub enum SessionEffect {
    InjectLocal(InputEvent),
    SendRemote(InputEvent),
    SetLocalCursor(Position),
    ReleaseLocal(HeldInput),
    ReleaseRemote,
    ControlChanged(ControlTarget),
}
```

确切枚举应在迁移时通过测试驱动收敛；上述名称表达 seam，而不是冻结最终代码。

Core 必须维护以下不变量：

1. 任一物理按键或按钮在任一时刻最多由一个目标拥有。
2. 控制权跨屏迁移时，旧目标先释放，随后新目标恢复仍被物理按住的输入。
3. peer 断开、会话停止或执行失败时，已注入输入最终得到释放。
4. 过期或重复的无可靠运动事件不会被再次执行。
5. 路由状态变更与产生的 effect 顺序确定且可测试。

### 6.2 Application 与 Runtime

Application seam 对所有表现层提供同一接口：

```rust
pub enum AppCommand {
    StartHost(HostConfig),
    StartClient(ClientConfig),
    Stop,
    UpdateConfig(AppConfig),
}

pub enum AppEvent {
    StatusChanged(RuntimeStatus),
    PeerChanged(Option<PeerSummary>),
    ControlChanged(ControlTarget),
    Faulted(AppFault),
}

pub struct RuntimeHandle {
    // command sender、event receiver 和关闭/等待能力
}
```

`RuntimeHandle` 的具体 channel 类型属于实现细节，不进入 Core。其接口必须说明：

- 命令的顺序保证；
- event 是增量事件还是完整快照；
- channel 满或接收端退出时的错误语义；
- `Stop` 的幂等性；
- handle drop 是否停止 runtime；
- 关闭完成前是否保证释放已注入输入。

`RuntimeStatus` 至少表达：

```text
Stopped
Starting
Listening / Connecting
Connected
Retrying
Stopping
Faulted
```

具体状态可细化，但 GUI 不得依赖 tracing 文本判断运行状态。

Runtime 应采用单写者模型：一个 supervisor 拥有活动会话状态，其他任务只发送事实或执行 effect。不得让多个网络/设备任务通过共享锁任意修改业务状态。

### 6.3 Platform Input Adapter

平台 Adapter 负责：

- 枚举和校验输入权限/设备；
- 将平台事件归一化为领域 `InputEvent`；
- 抓取或释放物理输入；
- 注入领域输入；
- 获取屏幕尺寸和光标位置；
- 将平台失败转换为分类明确的 Adapter 错误。

Tokio channel、`ReliableEvent` 和 wire sequence 不得出现在平台输入 Adapter 的外部 seam。当前 `spawn_capture(... mpsc::Sender<ReliableEvent>, watch::Sender<Option<Motion>>)` 必须在迁移中被替换。

平台 Adapter 还必须提供可验证的清理语义。macOS event tap、Linux device grab 和虚拟输入设备的生命周期必须由可拥有、可停止的 handle 表达，不能依赖进程退出回收。

### 6.4 Transport 与 Protocol Adapter

Transport 负责连接、可靠消息、无可靠运动消息、关闭和连接状态，不负责屏幕路由或按键所有权。

Protocol 负责领域消息与 wire DTO 之间的显式转换：

```text
Domain InputEvent
    ↕ conversion
Wire ReliableEvent / MotionDto
    ↕ postcard framing
QUIC stream / datagram
```

Linux evdev 的 `event_type/code/value` 可暂时保留在协议版本 2 中以维持兼容，但必须止于 Protocol/Platform Adapter。Core 不应继续以裸 `u16/u16/i32` 表示输入语义。

### 6.5 Diagnostics

Diagnostics 是旁路观察者，不是业务层。

```rust
pub enum DiagnosticEvent {
    InputBatchProcessed { count: usize, elapsed: Duration },
    MotionDropped { sequence: u64, reason: DropReason },
    QueueDepth { queue: QueueName, depth: usize },
    ConnectionAttempt { attempt: u32 },
}
```

Runtime/Core 可以发布结构化事实；日志、指标和未来 GUI 诊断页面消费这些事实。诊断消费者不得修改会话状态。业务所需的超时和错误是领域/Runtime 事件，不应伪装成日志再被解析。

诊断通道拥塞不得阻塞输入热路径。可丢弃的指标与不可丢弃的应用状态必须使用不同的传递策略。

### 6.6 CLI Adapter

CLI 负责：

- 解析参数；
- 将参数转换为 `AppCommand`；
- 将 `AppEvent`/状态渲染为终端输出和退出码；
- 将 Ctrl-C 转换为 `Stop`。

CLI 不再包含 `host_connection`、`client_connection`、路由或重试循环。证书生成可以作为独立应用用例保留，但不应与会话运行流程耦合。

### 6.7 GPUI Adapter

GPUI 只保存 UI 投影和 UI 临时状态：

```rust
struct RflowAppModel {
    runtime_status: RuntimeStatus,
    peer: Option<PeerViewModel>,
    settings: SettingsForm,
    // RuntimeHandle、长期存活的 GPUI tasks/subscriptions
}
```

GPUI action 转换为 `AppCommand`；Runtime 的 `AppEvent` 在 GPUI context 中更新 entity 并触发重绘。

以下 GPUI 类型不得出现在 Core、Protocol、Transport 或 Platform Input：

- `gpui::App` / `AsyncApp`；
- `gpui::Entity<T>`；
- `gpui::Context<T>`；
- `gpui::Task<T>`；
- `gpui::Subscription`；
- View/Render 相关类型。

Quinn 和当前 Tokio 工作负载应继续运行在 Runtime 管理的专用线程/运行时中。GPUI 主线程只发送命令和应用状态，不执行阻塞输入采集或网络循环。

GPUI 长期监听任务和 subscription 必须被明确持有；其 drop 行为不得意外终止 Runtime。窗口关闭、隐藏到托盘和应用退出必须映射为不同的显式生命周期命令。

## 7. 状态分类

系统状态必须按所有权分类，不能放入一个全局结构：

| 分类 | 示例 | 所有者 |
|---|---|---|
| Configuration | 地址、证书路径、重试窗口、屏幕布局 | 配置模块/Application |
| Desired state | 用户要求运行 host/client 或停止 | Application |
| Domain state | 当前控制目标、光标位置、按下集合 | Core |
| Runtime state | connecting、connected、retrying、task health | Runtime |
| Diagnostic state | 延迟、队列深度、丢包、最近错误上下文 | Diagnostics |
| UI state | 当前页面、编辑中的表单、弹窗 | GPUI |

`RuntimeStatus` 是对 Runtime state 的稳定投影，不暴露 task、channel 或 Quinn 对象。

## 8. 错误与生命周期语义

错误至少按以下类别对 Application 暴露：

- 配置无效；
- 权限不足；
- 平台能力不可用；
- 连接或认证失败；
- 协议不兼容；
- peer 断开；
- 内部任务意外终止；
- 清理失败。

错误必须包含适合 UI 展示的稳定分类和适合诊断的 source/context。GUI 不解析 `anyhow` 格式化字符串来决定操作。

生命周期要求：

1. `Start*` 只能从允许的状态进入；重复启动返回明确结果，不能静默创建第二套 capture/runtime。
2. `Stop` 幂等，并等待输入释放、设备 ungrab 和连接关闭达到定义的完成点。
3. Runtime 故障必须进入 `Faulted` 或重试状态，并发布 `AppEvent`。
4. client 的 `retry_for` 属于 Runtime 策略；CLI 与 GUI 不实现外部 `while`。
5. GUI 暂时失去观察者不应自动停止后台 Runtime，除非显式生命周期策略如此配置。

## 9. 并发与性能

- 输入业务状态由单一 supervisor 串行写入，以避免锁竞争和顺序歧义。
- 按键、按钮、进入/离开屏幕和释放命令使用有序可靠路径。
- 高频运动可以使用覆盖旧值或有界丢弃策略，但屏幕切换 effect 不得被运动合并吞掉。
- Application event 不得逐个复制全部鼠标运动给 GUI；GUI 只接收用户可感知的状态和限频诊断数据。
- 慢日志、指标或 GUI 不得对输入热路径形成反压。
- 所有 channel 必须有明确容量、满载策略和关闭语义，禁止无理由使用无界队列。

## 10. 测试策略

模块接口同时是主要测试 seam。

### 10.1 Core 测试

Core 测试不启动 Tokio、QUIC 或系统输入设备。至少覆盖：

- 本地与远端屏幕间双向切换；
- 不同尺寸屏幕的坐标映射；
- 按住键/按钮跨屏后在正确目标恢复；
- 拖动跨屏期间按钮所有权不丢失；
- 返回本机、断连和停止时释放所有远端输入；
- stale motion 被过滤；
- 相同事件序列产生相同 effect 序列。

### 10.2 Runtime 测试

使用 fake Adapter 通过正式 seam 测试：

- Start/Stop 状态迁移；
- 重连窗口到期和成功恢复；
- Adapter 任务异常退出；
- effect 执行失败后的清理；
- 命令和设备事件并发到达时的确定顺序；
- Application event 投影。

### 10.3 Adapter 测试

- Protocol 编解码与版本兼容测试；
- QUIC loopback 集成测试；
- 各平台输入映射单元测试；
- 双机手工测试用于验证操作系统权限、抓取和真实注入行为。

双机测试不能替代 Core/Runtime 的自动测试。

## 11. 建议代码组织

第一阶段可以在单 crate 内按模块形成 seam，避免迁移期间同时承担 workspace 拆分风险：

```text
src/
  core/
    session.rs
    input.rs
    topology.rs
  runtime/
    supervisor.rs
    application.rs
  adapters/
    platform/
    transport_quic.rs
    protocol_v2.rs
    diagnostics_tracing.rs
  cli.rs
  main.rs
```

当依赖稳定后再考虑拆成 workspace crates：

```text
rflow-core
rflow-runtime
rflow-protocol
rflow-platform
rflow-cli
rflow-gui
```

拆 crate 是强化依赖方向的手段，不是本规格完成的前提。

## 12. 迁移计划

### 阶段 A：建立纯 Core

1. 定义平台无关的领域输入类型。
2. 将 `CursorRouter`、`PressedState` 和切屏决策收拢进 `DesktopSession`。
3. 将 `route_reliable`、`route_motion`、`replay_held_inputs` 和 `release_all` 中的业务顺序转换为 `SessionEvent -> SessionEffect`。
4. 用纯单元测试冻结当前已验证行为，特别是键盘迁移和按住拖动。

### 阶段 B：建立 Runtime/Application seam

1. 引入 `AppCommand`、`AppEvent`、`RuntimeStatus` 和 `RuntimeHandle`。
2. 将 host/client、握手、heartbeat、重试和关闭迁入 `RuntimeSupervisor`。
3. 使用 Adapter 执行 Core effect。
4. 将 tracing 改为 Runtime/Diagnostics 对结构化事实的消费。

### 阶段 C：迁移现有 Adapter 与 CLI

1. 平台输入不再发送 protocol DTO。
2. Protocol 显式转换领域与 wire 类型。
3. CLI 只解析/渲染并调用 Application seam。
4. 保持现有 CLI 参数和协议兼容，除非另有规格批准破坏性变更。

### 阶段 D：接入 GPUI

1. 增加 GUI crate/module 和 `RflowAppModel`。
2. 建立 GPUI 与 `RuntimeHandle` 的命令/事件桥。
3. 实现状态、权限、错误和启动/停止展示。
4. 验证窗口生命周期不会意外 drop Runtime 或遗留被按下输入。

### 阶段 E：可选 daemon 化

若产品需要登录启动、托盘常驻、权限隔离或 GUI 独立重启，则保持 Application 语义不变，将进程内 channel Adapter 替换为 IPC Adapter。此阶段单独立项，不在当前迁移中预实现 IPC。

## 13. 验收标准

本规格的架构迁移在满足以下条件时完成：

1. Core 可在不启用 Tokio、Quinn、GPUI 和平台输入依赖的情况下测试。
2. host/client 的路由与输入所有权决策不再位于 `main.rs`。
3. CLI 通过 `AppCommand`/`AppEvent` 或等价的单一 Application seam 工作。
4. 平台输入 seam 不暴露 `ReliableEvent`、Quinn 或 Tokio channel。
5. Protocol DTO 与领域输入之间存在显式转换。
6. Runtime 拥有重试、heartbeat、任务监督和 shutdown。
7. 日志/指标消费者移除后，业务行为保持不变。
8. 自动测试覆盖跨屏按键、按住拖动、断连释放和 stale motion。
9. Runtime 提供足够稳定的状态投影，使未来 GPUI 无需读取日志或内部 task 状态。
10. 双机回归测试确认光标、键盘、按住拖动、切回本机和断连清理均正常。

## 14. 架构决策摘要

- 采用纯 Core + 单写者 Runtime + 外部 Adapter + 多表现层结构。
- GPUI 是表现层 Adapter，不是业务状态容器。
- Tokio/Quinn 保留在 Runtime，不迁入 GPUI UI 线程。
- Diagnostics 为旁路观察，不与业务控制流混合。
- CLI 与 GUI 共用 Application seam。
- 先在单 crate 中形成正确 seam，再根据依赖稳定性拆 workspace。
- 为未来 daemon 保留替换 Runtime transport 的能力，但当前不提前实现 IPC。
