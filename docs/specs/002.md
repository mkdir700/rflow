# Spec 002: 零配置入门、设备信任与屏幕拓扑 CLI

- 状态：Draft
- 日期：2026-08-30
- 范围：CLI 入门流程、设备身份、首次配对确认、自动检测、拓扑展示及未来 GPUI seam
- 依赖：Spec 001 的 Core/Application/Runtime/Adapter 分层

## 1. 背景

当前 rflow 要求用户手动生成和复制 server 证书、选择 Linux evdev 设备、填写逻辑屏幕
尺寸，并用相对方向描述两台设备的位置。这些参数适合调试 MVP，但不适合作为普通用户的
入门接口：设备路径属于平台细节，逻辑尺寸难以判断，`direction` 在三台及更多设备时缺少
明确参照物，手动复制证书也容易出错。

本规格将默认流程收敛为：server 自动建立本机身份，client 使用 IP 或 hostname 连接，
server 对未知设备进行显式确认，双方记住长期身份；输入设备、屏幕和逻辑尺寸默认自动
发现；CLI 能渲染与未来 GPUI 相同的屏幕拓扑快照。

## 2. 目标

1. 普通用户可以通过 `rflow host` 和 `rflow client <host>` 完成首次连接。
2. 本机没有身份时自动生成，不要求先执行 `keygen`。
3. 未知 client 必须由 server 端明确确认后才能成为可信设备。
4. 双方显示由当前握手派生的相同短认证码，供用户核对。
5. 已配对设备在后续连接中自动完成双向身份验证。
6. 身份发生非预期变化时拒绝连接，不允许静默覆盖信任记录。
7. server 必须在配对确认完成后才抓取物理输入设备。
8. Linux 输入设备和各平台逻辑屏幕尺寸默认自动发现，手动参数只作为高级覆盖。
9. 用具名设备和屏幕拓扑表达多设备布局，不再依赖无参照物的单一 `direction`。
10. CLI 和未来 GPUI 读取同一个权威拓扑快照。

## 3. 非目标

本规格不要求：

- 通过互联网中继发现设备；
- 无用户确认的自动信任；
- 账号、云同步或中心证书服务；
- 在本阶段完成 GPUI 页面；
- 自动推断任意多屏的物理排列；
- 远程绕过本机权限模型安装驱动或修改系统安全设置；
- 保留当前基于手动复制 server 证书的 CLI 兼容性。

## 4. 用户体验

### 4.1 首次启动 server

```bash
rflow host
```

若身份不存在，rflow 自动创建并输出：

```text
Generated device identity
Device: linux-desktop
Fingerprint: SHA256:8D:21:...

Listening on 0.0.0.0:24801
Waiting for devices...
```

身份必须存入操作系统约定的应用数据目录，不能依赖当前工作目录：

```text
Linux:   $XDG_CONFIG_HOME/rflow（未设置时使用 ~/.config/rflow）
macOS:   ~/Library/Application Support/rflow
Windows: %APPDATA%\rflow
```

私钥文件必须仅允许当前用户访问。若无法保证权限，启动失败并给出明确错误。

### 4.2 client 首次连接

`TARGET` 接受 IP、hostname 或显式端口；未给端口时使用 `24801`：

```bash
rflow client 192.168.1.50
rflow client linux-desktop.local
rflow client linux-desktop.local:24801
```

未知 server 与未知 client 进入待确认状态。client 输出：

```text
Connecting to linux-desktop.local:24801...

Untrusted server
Device: linux-desktop
Fingerprint: SHA256:8D:21:...
Pairing code: 482 731

Waiting for confirmation on linux-desktop...
```

server 输出：

```text
Pairing request

Request: p-7f31
Device: macmini
Address: 192.168.1.82
Fingerprint: SHA256:42:A7:...
Pairing code: 482 731

Accept this device? [y/N]
```

只有输入 `y` 或 `yes` 才接受；空输入、EOF、超时和其他输入均拒绝。接受后双方分别以本机
原子写入保存信任记录；任一端持久化失败都不得进入业务会话。

### 4.3 非交互确认

server 可能由 systemd、launchd 或 GUI 启动，因此确认不能只依赖启动它的 stdin。CLI
必须支持管理待确认请求：

```bash
rflow peers pending
rflow peers accept p-7f31
rflow peers reject p-7f31
```

待确认请求至少显示请求 ID、设备名、来源地址、指纹、短认证码和到期时间。管理命令通过
本机受权限保护的 Application/daemon seam 操作同一个 Runtime 状态，不能启动第二套网络
会话或直接改写 Runtime 内存。

如果尚未实现 daemon IPC，首个迭代可以只支持前台 `[y/N]`，但领域命令和状态必须按未来
独立管理终端的需求设计，不能把 `stdin.read_line()` 放进 Transport 或 Core。

### 4.4 后续连接

已配对设备后续连接不再询问：

```text
Trusted device: linux-desktop
Connection established.
```

若同一设备标识或已知 endpoint 提供不同身份，必须拒绝：

```text
SECURITY ERROR: identity for linux-desktop has changed.

Expected: SHA256:8D:21:...
Received: SHA256:91:BC:...

Connection refused.
Review the device and remove the old trust explicitly:
  rflow peers forget linux-desktop
```

不得提供在同一次失败连接中跳过检查或自动接受新证书的选项。

### 4.5 信任管理

```bash
rflow peers
rflow peers pending
rflow peers accept <request-id>
rflow peers reject <request-id>
rflow peers forget <device-id-or-name>
```

`forget` 必须要求交互确认；脚本模式可使用明确的 `--yes`。遗忘设备同时移除其长期信任，
但拓扑中的离线屏幕记录是否删除必须单独询问或由独立命令处理，避免安全身份管理意外破坏
用户布局。

### 4.6 高级证书覆盖

普通流程不出现证书参数。高级用户可以指定本机身份：

```bash
rflow host --identity-cert host-cert.der --identity-key host-key.der

rflow client linux-desktop.local \
  --identity-cert macmini-cert.der \
  --identity-key macmini-key.der
```

也可以显式固定预期 server 身份，用于自动化部署：

```bash
rflow client linux-desktop.local --server-cert host-cert.der
```

`--server-cert` 表示信任锚；`--identity-cert/--identity-key` 表示本机身份。不得继续使用含义
模糊的 client `--cert` 同时承担两种角色。手动指定身份不会绕过 server 对未知 peer 的授权
策略，除非该 peer 已预置在信任存储中。

## 5. 身份与配对安全模型

### 5.1 长期设备身份

每台设备拥有独立的长期私钥和证书。`DeviceId` 从规范化公钥摘要派生，不从 hostname、IP
或用户可修改的显示名称派生。设备名称只用于展示，可以重复或修改。

信任记录至少包含：

```rust
pub struct TrustedPeer {
    pub device_id: DeviceId,
    pub display_name: String,
    pub certificate: Vec<u8>,
    pub fingerprint: Fingerprint,
    pub first_seen_at: SystemTime,
    pub last_seen_at: Option<SystemTime>,
}
```

Core 中不能使用 `SystemTime` 或证书字节；上例属于 Identity/Trust Adapter 的持久化模型。

### 5.2 双向认证

配对完成后的业务连接必须双向验证长期设备身份。仅由 client 固定 server 证书不足以阻止
任意局域网设备控制或加入拓扑。Transport 负责 TLS/QUIC 证明，Trust policy 负责决定该
身份是否获准连接；两者不能混为一个布尔值。

### 5.3 短认证码

短认证码（SAS）必须由本次握手 transcript、双方长期公钥和双方随机数通过带域分离的
密码学散列/KDF 派生。两端独立计算并显示相同结果，不能由一端生成后直接告知另一端。

首版使用六位十进制码，按 `NNN NNN` 展示。它只用于人工对比，不作为密钥、证书或远程
授权 token。配对请求必须短时有效、单次使用，并限制并发数和请求速率。

具体握手协议、算法选择、transcript 编码和降级保护在实现前需要单独的安全设计评审与
协议版本定义；不得临时拼接字符串后直接散列。

### 5.4 TOFU 的边界

该模型是带 server 端确认的首次使用信任，不保证未核对短码时免受首次连接中间人攻击。
CLI 必须明确提示用户比较两端短码。远程无人值守部署应使用预置证书或预置 peer 身份，
不能自动接受首次连接。

## 6. 输入抓取与确认时序

server 只有在 peer 已可信、连接已建立且会话准备完成后才能 grab 物理输入设备：

```text
Stopped
  → Starting
  → Listening
  → PairingPending
  → Authenticating
  → Connected
  → CapturingInput
```

拒绝、超时或握手失败直接回到 `Listening`，不得短暂 grab 输入。已有会话期间的新配对请求
不得改变当前输入控制权。Runtime 必须能把待确认事件发布给 CLI/GPUI：

```rust
pub enum AppEvent {
    PairingRequested(PairingRequestSummary),
    PairingExpired(PairingRequestId),
    PeerTrusted(PeerSummary),
    // existing events...
}

pub enum AppCommand {
    AcceptPairing(PairingRequestId),
    RejectPairing(PairingRequestId),
    ForgetPeer(DeviceId),
    // existing commands...
}
```

CLI 负责读取 stdin 并把用户意图转换为 `AppCommand`；Runtime 和 Core 不读取终端。

## 7. 自动设备与屏幕发现

### 7.1 输入设备

Linux host 未指定高级覆盖时自动枚举 evdev：

- 根据 capability 识别键盘、相对指针和按钮；
- 支持键盘与鼠标来自同一复合设备或多个设备；
- 排除 rflow 创建的 uinput 设备和明显的虚拟回环设备；
- 去重同一物理设备暴露的别名；
- 在 grab 前输出最终选择；
- 权限不足时列出具体路径并给出可执行的修复提示。

手动 `--device <PATH>` 仅作为覆盖；只要提供至少一个，该次启动就不再自动补选其他设备，
避免产生不可见的混合配置。

### 7.2 屏幕

各平台 Adapter 返回稳定屏幕标识、显示名称、逻辑尺寸、缩放和当前位置。普通用户不填写
`--size`。高级覆盖必须绑定到具名屏幕，而不是一个进程级尺寸。

多显示器设备的每块显示器都是独立 `ScreenNode`，但共享同一 `DeviceId`。自动检测失败时
启动可以进入可诊断的 `ConfigurationRequired` 状态，不得猜测一个可能错误的尺寸后抓取输入。

## 8. 多设备屏幕拓扑

`direction` 只能表达两屏关系，不能作为长期领域模型。目标模型显式描述屏幕和连接边：

```rust
pub struct ScreenTopology {
    pub revision: u64,
    pub screens: Vec<ScreenNode>,
    pub links: Vec<ScreenLink>,
}

pub struct ScreenNode {
    pub screen_id: ScreenId,
    pub device_id: DeviceId,
    pub name: String,
    pub logical_size: ScreenSize,
    pub online: bool,
}

pub struct ScreenLink {
    pub from: ScreenEdge,
    pub to: ScreenEdge,
}
```

例如：

```text
linux-desktop/display-1.right ↔ macmini/display-1.left
macmini/display-1.bottom      ↔ laptop/display-1.top
```

拓扑必须验证：ID 唯一、link 端点存在、同一边的冲突策略明确、从当前屏幕到目标屏幕可达，
并拒绝会造成不确定路由的配置。八方向布局可以作为导入旧双屏配置的表示，但新 CLI/GUI
编辑操作必须明确指出源屏幕和目标屏幕。

## 9. CLI 拓扑可视化

```bash
rflow layout
rflow layout --watch
rflow layout --json
```

默认输出可读的 Unicode 布局，并标记本机、在线状态和逻辑尺寸：

```text
Screen layout

                   ┌────────────────────┐
                   │ macmini            │
                   │ display-1 1920×1080│
                   └─────────┬──────────┘
                             │
┌────────────────────┐  ┌────┴───────────────┐
│ laptop             │  │ linux-desktop ★   │
│ display-1 1440×900 │──│ display-1 2560×1440│
└────────────────────┘  └────────────────────┘

★ This device
```

- `--watch` 订阅权威 `RuntimeSnapshot`，设备或拓扑变化时重绘；
- `--json` 输出有版本号的机器可读 schema，不混入日志；
- 非 TTY、`NO_COLOR` 或 `TERM=dumb` 时关闭颜色和动态重绘；
- 无法完整二维排布时仍输出节点/link 列表，并明确报告冲突或断链；
- renderer 是纯表现层，只读拓扑，不修正或推断业务状态；
- GPUI 使用同一 `ScreenTopology` 和变更命令，不解析 CLI 渲染文本。

## 10. 分层与模块边界

```text
CLI / GPUI
    │ AppCommand / AppEvent / RuntimeSnapshot
    ▼
Application + Runtime
    ├── Identity/Trust store adapter
    ├── Pairing protocol adapter
    ├── Platform discovery adapter
    ├── QUIC transport adapter
    └── Core: topology validation and routing
```

- Core：设备/屏幕 ID、拓扑规则、路由与纯状态转换；
- Runtime：配对生命周期、确认命令排序、连接监督、抓取时机和权威快照；
- Transport/Pairing：握手、双向证明、SAS 所需 transcript；
- Trust store：身份和 peer 的原子持久化、权限及迁移；
- Platform：设备/屏幕发现与输入抓取；
- CLI/GPUI：展示请求、收集确认意图、渲染拓扑。

诊断日志不得作为确认通道、信任数据库或 GUI 状态源。

## 11. 故障与恢复

- 身份生成后证书写入成功但私钥写入失败：清理不完整身份并失败，不得留下可误用状态；
- 信任记录持久化失败：配对失败，不进入已信任业务会话；
- stdin 不可用：保留待确认请求，提示使用管理命令；
- 请求到期：双方关闭配对连接并发布 `PairingExpired`；
- hostname 解析到多个地址：按连接策略尝试，但身份必须与同一目标约束匹配；
- 已信任设备改名或换 IP：通过稳定 `DeviceId` 识别，允许更新展示元数据；
- 相同名称对应不同身份：作为不同设备展示，不以名称覆盖；
- peer 断开：释放已注入输入，拓扑节点标记离线但不自动删除；
- 自动检测结果变化：先发布配置变化，未经安全迁移不得在按键按下期间更换抓取设备。

## 12. 迁移与实施顺序

### Phase 1：自动身份与简化目标地址

- 自动创建本机身份；
- `client` 接受无端口 IP/hostname；
- 明确区分本机身份和 server 信任锚；
- 保留手动身份覆盖作为高级功能。

### Phase 2：首次配对与信任存储

- 双向身份握手；
- server 前台确认；
- SAS、过期、限流与证书变更拒绝；
- `peers` 查询和遗忘。

### Phase 3：可管理的待确认请求

- `peers pending/accept/reject` Application seam；
- 本机 daemon IPC 或等价的单 Runtime 管理通道；
- 后台运行兼容。

### Phase 4：自动发现

- Linux evdev 自动选择；
- Linux/macOS/Windows 屏幕和逻辑尺寸检测；
- 高级覆盖和可操作的权限诊断。

### Phase 5：多屏拓扑与渲染

- `ScreenTopology`、验证和持久化；
- 多设备路由；
- `rflow layout`、`--watch`、`--json`；
- 为 GPUI 提供相同快照和编辑命令。

Phase 1 不得通过“信任任意证书”伪装成自动配对。若 Phase 2 尚未完成，自动身份只能用于
显式预置证书的部署，普通零证书首次连接必须保持不可用。

## 13. 验收标准

1. 全新安装的 server 执行 `rflow host` 可安全生成身份并监听。
2. 全新 client 可用 IP、hostname 或带端口地址发起连接。
3. 未知 peer 未经 server 明确接受，不能建立输入会话或触发设备 grab。
4. 两端对同一握手独立生成相同 SAS；篡改任一 transcript 字段会产生不同结果。
5. 接受后双方重启仍可互认，且不再次询问。
6. 已知设备身份变化时连接失败，旧信任不会被覆盖。
7. 待确认请求会过期、限流，拒绝后不能复用。
8. 信任写入使用原子替换，私钥和本机管理接口满足平台权限要求。
9. 默认 host 无需填写 evdev 路径或逻辑尺寸；失败时给出具体诊断。
10. 三台设备和单设备多屏可由显式拓扑无歧义表达。
11. `rflow layout` 与 Runtime 权威拓扑快照一致，`--json` 输出稳定且不混入日志。
12. CLI 与未来 GPUI 均只通过 Application seam 确认配对和修改布局。
13. Linux、macOS 和 Windows 的条件编译、单元测试和端到端握手测试通过。

## 14. 实现前待定事项

以下内容必须在进入对应 Phase 前形成明确决策或 ADR：

1. 双向 TLS 使用自签长期证书、私有 CA，还是应用层签名身份；
2. 配对握手协议和 SAS 的具体算法、域分离与 transcript 编码；
3. 信任存储采用受权限保护文件还是系统 keychain，以及各平台迁移策略；
4. daemon IPC 的认证与单实例模型；
5. hostname 与设备身份的绑定和多地址连接策略；
6. 多屏 link 冲突、循环和几何坐标的最终规则；
7. CLI 拓扑编辑命令语法及其与 GPUI 拖拽操作的共同 command model。
