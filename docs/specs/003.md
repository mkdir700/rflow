# Spec 003: 持久化屏幕拓扑与 CLI 布局管理

- 状态：Implemented
- 日期：2026-08-30
- 范围：设备屏幕清单、持久布局、CLI 布局编辑、多 peer 路由及旧 `direction` 迁移
- 依赖：Spec 001 的 Core/Application/Runtime/Adapter 分层、Spec 002 的设备身份与配对

## 1. 背景

rflow 当前同时存在两套布局表达：运行中的双屏会话使用 `HostConfig.direction`、
`ScreenDirection` 和 `CursorRouter`；管理接口则使用持久化的 `ScreenTopology`、具名屏幕和
边缘 link。后者已经能够验证和展示多屏拓扑，但尚未成为生产会话的路由依据。因此，用户
即使保存了 topology，启动 host 时仍需要传入 `--direction`，且实际切屏方向不一定与
`rflow layout` 展示的内容一致。

这种过渡状态不能长期保留。布局必须只有一个权威来源，并且能够表达一台设备包含多个
显示器、多个 peer 同时在线、离线屏幕保留位置以及环形拓扑。设备信任和屏幕位置也必须
保持不同职责：信任回答“这是谁以及是否允许连接”，布局回答“它的哪一块屏幕放在哪里”。

本规格将持久化屏幕拓扑定义为唯一布局来源。CLI 通过相对位置命令管理方向，Runtime 将
持久布局与在线屏幕清单合并后交给 `TopologyRouter`，不再从 host 启动参数读取方向。

## 2. 目标

1. 配置一次布局后，后续执行 `rflow host` 无需重复传入方向。
2. `rflow layout` 展示的拓扑与 Runtime 实际使用的切屏拓扑一致。
3. 方向表示为两个具体屏幕边缘之间的 link，而不是设备级或进程级枚举值。
4. 支持多设备、多显示器、离线屏幕、未放置屏幕和确定性的环形拓扑。
5. `peers` 只管理安全身份，但可以展示设备的屏幕数量和布局摘要。
6. CLI 提供易用的相对位置命令，同时保留精确的 edge link 命令供脚本和高级用户使用。
7. 日常 CLI 修改自动处理 revision；完整文件导入继续使用显式乐观并发控制。
8. 布局修改经过统一 Application seam，由一个深模块完成解析、验证、冲突处理、revision
   递增和原子持久化。
9. 旧 `--direction` 可以迁移为首个持久 link，最终从生产路径删除。

## 3. 非目标

本规格不要求：

- 自动推断屏幕的真实物理位置；
- 支持对角角点 link；持久模型只允许四个正交边缘；
- 跨账号或云端同步布局；
- 允许未受信任设备参与输入路由；
- 用设备名或显示器名替代稳定 ID 作为持久身份；
- 在 CLI 中实现图形化拖拽画布；未来 GUI 必须复用相同命令和快照；
- 保证迁移期间旧版程序能够读取新版布局存储。

## 4. 权威模型

系统将安全身份、动态发现和用户布局分为三类状态：

```text
TrustStore              ScreenInventory             LayoutStore
设备身份与证书           当前发现的屏幕事实           用户保存的布局意图
        └──────────────────────┬───────────────────────┘
                               ▼
                       ResolvedTopology
                               ▼
                         TopologyRouter
```

### 4.1 TrustStore

`TrustStore` 只保存安全身份和 endpoint 绑定：

```rust
pub struct TrustedPeer {
    pub device_id: DeviceId,
    pub display_name: String,
    pub certificate: Vec<u8>,
    pub first_seen_at: u64,
    pub last_seen_at: Option<u64>,
}
```

不得向 `TrustedPeer` 增加 `direction`。一台设备可能有多个显示器，每个显示器可以连接到
不同邻居；设备级方向无法准确表达这种关系。

遗忘 peer 时必须删除其信任和 endpoint 绑定，但不得静默删除布局。布局中的相关屏幕变为
离线或不可解析，用户通过独立的 layout 命令决定是否清理，避免安全操作意外破坏布局。

### 4.2 ScreenInventory

`ScreenInventory` 是动态事实，不直接作为持久布局。每台设备在认证完成后报告屏幕清单：

```rust
pub struct ScreenDescriptor {
    pub screen_id: ScreenId,
    pub device_id: DeviceId,
    pub name: String,
    pub logical_size: ScreenSize,
    pub primary: bool,
}
```

`ScreenId` 必须跨进程重启稳定，建议格式为：

```text
<DeviceId>/<platform-stable-screen-id>
```

显示名称只用于展示和命令解析，不能成为持久主键。在线状态由连接和平台发现派生，不写入
用户布局。屏幕断开时保留其已知描述供展示，但 Runtime 不得将控制权切换到离线屏幕。

### 4.3 LayoutStore

`LayoutStore` 只保存用户意图：

```rust
pub struct ScreenLayout {
    pub schema_version: u16,
    pub revision: u64,
    pub links: Vec<ScreenLink>,
    pub size_overrides: Vec<ScreenSizeOverride>,
}

pub struct ScreenLink {
    pub from: ScreenEdge,
    pub to: ScreenEdge,
}
```

持久 link 连接两个具体屏幕的相对边。例如：

```text
linux/DP-1.right ↔ macmini/main.left
```

LayoutStore 必须原子写入，并使用 revision 执行 compare-and-swap。成功修改后 revision 加一；
revision 不匹配时不得部分应用修改。

### 4.4 ResolvedTopology

Application 将 LayoutStore 与 ScreenInventory 合并为 `ResolvedTopology`。快照至少包含：

- 当前 layout revision；
- 所有已知屏幕及其设备归属；
- 实际逻辑尺寸及可选 size override；
- 在线、本机、可信和已放置状态；
- 已解析 link 及无法解析 link 的原因。

结构验证与运行可达性是两件事。引用离线屏幕的 link 可以结构有效并保留在布局中，但不具备
当前可路由性。CLI 必须明确显示这种状态。

## 5. 拓扑不变量

布局模块必须集中维护以下不变量：

1. `ScreenId` 非空并且唯一。
2. 一个 `ScreenEdge` 最多参与一个 link。
3. link 两端不能是同一个 edge。
4. link 只能连接相对边：Top ↔ Bottom、Left ↔ Right。
5. link 是双向的，不能分别维护两个方向记录。
6. 允许 disconnected screen；它们可展示但不能通过指针进入。
7. 允许环；路由由当前到达的具体 edge 决定，不做图级方向猜测。
8. 目标屏幕离线、未受信任或没有活动连接时，指针停留在当前屏幕边缘。
9. size override 必须为正数，并且只影响坐标映射，不改变平台检测结果。
10. 所有复合修改必须在单次 revision 中原子完成。

## 6. CLI 用户体验

### 6.1 查看布局

```bash
rflow layout
rflow layout --watch
rflow layout --json
```

默认输出屏幕关系图、link、revision 以及异常状态。`--watch` 订阅或轮询同一 Runtime
权威快照；`--json` 输出版本化机器可读结构，不混入日志。

### 6.2 查看屏幕清单

```bash
rflow layout screens
```

示例：

```text
SCREEN              DEVICE       SIZE        STATUS   PLACEMENT
linux/eDP-1         linux        1920×1080   online   local
linux/DP-1          linux        2560×1440   online   right of linux/eDP-1
macmini/main        macmini      2560×1440   online   right of linux/DP-1
windows/display-1   windows      1920×1080   offline  unplaced
```

CLI 可以接受唯一的设备名或屏幕名作为简写，但输出应同时展示可复制的稳定 screen ID。

### 6.3 使用相对位置管理方向

普通用户使用 `place`：

```bash
rflow layout place macmini/main --right-of linux/DP-1
rflow layout place windows/display-1 --left-of linux/eDP-1
rflow layout place linux/DP-1 --above linux/eDP-1
rflow layout place projector/main --below linux/eDP-1
```

四个位置选项互斥：

```text
--left-of
--right-of
--above
--below
```

例如：

```bash
rflow layout place macmini/main --right-of linux/DP-1
```

必须转换为一个领域 link：

```text
linux/DP-1.right ↔ macmini/main.left
```

若一个设备恰好有一个已知屏幕，允许设备级简写：

```bash
rflow layout place macmini --right-of linux
```

若任一设备有多个屏幕，命令必须拒绝并列出候选项，不能默认选择 primary screen：

```text
Device "linux" has multiple screens:
  linux/eDP-1
  linux/DP-1

Specify a screen explicitly.
```

### 6.4 冲突与替换

若目标 edge 已参与 link，`place` 默认拒绝：

```text
linux/DP-1.right is already linked to macmini/main.left
```

用户可以显式替换：

```bash
rflow layout place windows/display-1 --right-of linux/DP-1 --replace
```

`--replace` 必须在同一事务中删除冲突 link 并创建新 link。不得先提交 unlink，再单独提交
link，从而短暂暴露半完成布局。

### 6.5 删除布局关系

删除一个具体边缘关系：

```bash
rflow layout unlink linux/DP-1.right
```

删除某屏幕参与的所有关系：

```bash
rflow layout unplace macmini/main
```

`unplace` 不删除屏幕清单、信任记录或 size override。

### 6.6 精确 edge 接口

高级用户和脚本可以直接管理 link：

```bash
rflow layout link linux/DP-1.right macmini/main.left
rflow layout unlink linux/DP-1.right
```

`place` 和 `link` 必须落到同一个 Application 布局命令模块，CLI 不自行编辑 JSON。

### 6.7 尺寸覆盖

```bash
rflow layout set-size macmini/main 2560x1440
rflow layout clear-size macmini/main
```

覆盖值用于坐标映射和布局展示，不修改平台报告的 `logical_size`。

### 6.8 导入与导出

```bash
rflow layout export > layout.json
rflow layout apply layout.json --expected-revision 12
```

完整文件 apply 必须继续要求显式 revision，因为用户可能长时间离线编辑文件。普通
`place/link/unlink/unplace/set-size` 命令由 CLI 先读取最新 revision，再提交原子领域命令，
不要求用户手动复制 revision。发生并发冲突时返回当前 revision，并要求用户重试。

### 6.9 peers 中的布局摘要

`rflow peers` 可以展示只读布局摘要，但不拥有布局修改接口：

```text
DEVICE      TRUSTED  ONLINE  SCREENS  PLACEMENT
macmini     yes      yes     1        right of linux/DP-1
windows     yes      no      2        partially placed
```

职责保持为：

- `rflow peers`：设备是谁、是否可信；
- `rflow layout`：设备的具体屏幕放在哪里；
- Runtime：哪些屏幕当前在线且可路由。

## 7. Application 布局接口

Application 提供少量领域命令，隐藏名称解析、冲突检测、revision 和持久化实现：

```rust
pub enum LayoutCommand {
    Link {
        from: ScreenEdge,
        to: ScreenEdge,
        replace: bool,
    },
    Unlink {
        edge: ScreenEdge,
    },
    Unplace {
        screen_id: ScreenId,
    },
    SetSizeOverride {
        screen_id: ScreenId,
        size: Option<ScreenSize>,
    },
    Replace {
        layout: ScreenLayout,
    },
}

pub struct RevisionedLayoutCommand {
    pub expected_revision: u64,
    pub command: LayoutCommand,
}
```

布局模块应是深模块：调用方只提交意图并接收新快照或结构化错误；验证、原子替换、冲突
link 计算、revision 递增和文件权限全部位于模块实现内部。CLI、GUI 和测试通过同一接口。

错误至少区分：

- screen 不存在或名称不唯一；
- edge 方向不相对；
- edge 已占用；
- revision 冲突；
- 屏幕未受信任；
- 布局持久化失败。

Management 协议不得只返回 `queued` 后把失败异步发布为全局 fault。布局命令应返回该命令
的确定结果，使 CLI 能准确显示冲突或持久化错误；成功响应包含新 revision 和权威快照。

## 8. 屏幕清单交换

双方完成身份认证后、开始输入会话前，必须交换本机 `ScreenDescriptor` 列表。协议要求：

1. 描述属于已认证的 `DeviceId`，远端不能声明另一个设备的屏幕。
2. 同一设备内 stable screen ID 唯一。
3. 尺寸必须为正数，并限制屏幕数量和字符串长度。
4. 清单更新可以在显示器热插拔时重新发送。
5. 断开连接后对应屏幕变为 offline，但布局 link 保留。
6. 协议版本不支持屏幕清单时，不得假装完整支持多屏拓扑。

Host 是输入拓扑的权威管理者。Client 报告屏幕事实，但不能直接修改 Host 的持久布局。

## 9. Runtime 路由

生产会话必须使用 `ResolvedTopology` 和 `TopologyRouter`，不再使用
`HostConfig.direction + CursorRouter`。Runtime 维护：

```text
ScreenId → DeviceId → ActivePeerConnection
```

路由流程：

1. Core 根据当前 screen、坐标和 motion 判断是否到达已连接 edge。
2. 边缘阻力满足后，`TopologyRouter` 返回目标 `ScreenId` 和映射坐标。
3. Runtime 根据目标 screen 找到设备及其活动连接。
4. 旧目标先释放已注入输入，新目标再恢复仍被物理按住的输入。
5. 目标不可路由时保持当前控制权，指针停在边缘，不丢失按键或按钮状态。

Runtime 必须支持同时监督多个 peer connection；“接受一个 Client 后退出 accept loop”的单连接
结构只能作为迁移阶段，不能作为本规格完成状态。

布局 revision 在会话中变化时，Runtime 必须原子替换路由拓扑。若当前活动远端屏幕被 unplace、
变为不可路由或被删除，Runtime 先释放远端输入，再安全返回本机屏幕。

## 10. 离线、热插拔与删除行为

- peer 离线：屏幕和 link 保留，状态显示 offline，不能进入。
- 屏幕热插拔：更新 inventory；稳定 ID 相同则恢复原布局。
- 屏幕永久移除：默认仍保留离线记录；用户显式执行清理命令。
- peer 被 forget：立即禁止其屏幕路由，但不自动删除布局。
- size 改变：未设置 override 时使用新 logical size；已有 override 时继续使用 override。
- 当前控制屏幕消失：释放目标端输入并回到本机可用屏幕。

后续可以增加显式清理命令：

```bash
rflow layout prune --offline
rflow layout remove-screen <screen>
```

这些命令必须明确列出将删除的 link，并要求确认或 `--yes`。

## 11. 迁移方案

### 阶段一：拆分状态

1. 将持久 `ScreenLayout` 与动态 `ScreenInventory` 分离。
2. 为存储增加 `schema_version` 和迁移器。
3. 保持现有 `rflow layout` 读取能力，但由 ResolvedTopology 渲染。

### 阶段二：CLI 编辑

1. 实现 `screens/place/link/unlink/unplace/set-size`。
2. Management 命令返回同步的结构化成功或失败结果。
3. GUI 后续复用相同 Application 命令，不直接改写存储。

### 阶段三：远端屏幕发现

1. 在认证后交换屏幕清单。
2. Host 合并本地和所有已认证 peer 的 inventory。
3. 在 `peers` 和 `layout screens` 中显示在线及布局摘要。

### 阶段四：运行时切换

1. 先让单 Client 会话改用 `TopologyRouter`。
2. 启动时若没有持久 link，但提供了旧 `--direction`，根据本机 primary screen 和远端唯一
   screen 生成一次性迁移 link，并明确提示用户。
3. 有持久 link 时拒绝同时使用 `--direction`，避免两个权威来源。
4. 验证迁移稳定后取消 `--direction` 的必填要求并最终删除该参数。

### 阶段五：多 peer

1. Runtime 持续 accept 并监督多个已认证连接。
2. 维护 screen 到连接的映射。
3. 验证跨三个及更多设备、环形拓扑、断线恢复和活动屏幕消失。
4. 删除生产路径中的 `CursorRouter` 和旧 `ScreenDirection` 会话逻辑。

## 12. 验收标准

本规格完成必须满足：

1. 用户执行一次 `layout place` 后，重启 Host 仍使用相同方向。
2. `rflow host` 在已有有效布局时不要求 `--direction`。
3. `rflow layout`、`--json`、GUI 快照和 Runtime 路由来自同一 revision。
4. 单屏设备名可简写，多屏设备名产生明确歧义错误。
5. edge 冲突默认拒绝，`--replace` 原子完成替换。
6. 并发修改不会丢失更新，revision 冲突不改变文件或 Runtime 快照。
7. 离线目标保留布局但不可进入，重新上线后自动恢复可路由状态。
8. peer forget 后不可路由，既有布局不会被静默删除。
9. 多显示器坐标按 effective size 正确映射。
10. 多 peer 可以同时在线，并能沿配置 link 双向切换。
11. 活动远端断线或布局被删除时，所有已注入输入得到释放并安全返回本机。
12. 生产代码不再从 `HostConfig.direction` 或 `CursorRouter` 决定屏幕切换。

## 13. 测试策略

Core 测试覆盖：

- link 不变量、环、disconnected screen 和坐标映射；
- 离线目标不可路由；
- 布局热替换时活动屏幕的确定性恢复；
- 边缘阻力在拓扑路由中保持一致。

Application/存储测试覆盖：

- 每种 `LayoutCommand` 的成功和结构化错误；
- `--replace` 的原子语义；
- stale revision 不产生任何修改；
- schema 迁移和崩溃安全写入；
- inventory 与 layout 合并但不反向污染持久用户意图。

Runtime/集成测试覆盖：

- 认证后屏幕清单交换；
- 单 peer 和多 peer 的 screen-to-connection 路由；
- peer 离线、重连和显示器热插拔；
- 切屏、断线和 topology 更新期间按键及按钮的释放顺序。

CLI 测试覆盖：

- 单屏简写与多屏歧义；
- 四种相对位置到 edge link 的转换；
- 冲突、`--replace`、revision 冲突和错误输出；
- 文本及 JSON 输出稳定且与 Runtime snapshot revision 一致。

## 14. 最终用户流程

首次配对后：

```bash
rflow peers
rflow layout screens
rflow layout place macmini --right-of linux
rflow host
```

多显示器场景：

```bash
rflow layout place linux/DP-1 --right-of linux/eDP-1
rflow layout place macmini/main --right-of linux/DP-1
rflow layout
```

以上布局配置持久化，并成为后续所有会话唯一的切屏依据。
